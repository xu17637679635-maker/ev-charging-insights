# EV 充电行为数据分析

> 用合成的充电会话数据，回答几个充电运营商真正关心的问题：**电网什么时候被压满、快充到底有多快、冬天有多糟、谁在依赖公共快充、多少时间浪费在"充完不走"上。**

**⚠️ 数据是合成数据。** 本文所有数字都是**行为模型的推论**，不是对真实城市的观测。这一点在第 6 节详细说明——请先读那一节再引用任何结论。

---

## 1. 三分钟看懂

一条命令跑完全流程：

```bash
python -m src.main
```

它会做三件事：**生成 14,755 条充电记录 → 跑 6 项分析 → 画 6 张图**。

### 数据长什么样

模拟 260 台电动车在 **300 天**（10 月 → 次年 7 月，横跨完整冬季到夏季）里的充电行为，输出：

| 文件 | 内容 |
|---|---|
| `data/raw/sessions.csv` | 每次充电的完整记录（时间、电量、功率、起止 SOC、温度……） |
| `data/raw/stations.csv` | 224 个充电桩（类型、额定功率、接口数、区域） |
| `data/raw/daily_summary.csv` | 每日汇总（次数、电量、气温） |

### 生成器是怎么工作的（关键设计）

我**没有直接编造"几点是高峰"**。生成器只编码三件事：

1. **通勤规律** —— 下班回家、上班停车、周末出行
2. **电池物理** —— 电量越高充电越慢（用实测曲线校准，见第 4 节）
3. **用户习惯** —— 目标充到多少、多久插一次枪

**"傍晚高峰"是这三者相互作用后自己涌现出来的**，不是塞进去的。这个区别很重要：它决定了分析阶段的发现是真"发现"，而不是把预设答案又读出来一遍。

## 2. 六项发现

### ① 负荷高度集中在傍晚，且主要来自家用慢充

![电网负荷的时间分布](figures/01_hourly_load.png)

- 19:00 达峰值 **35,573 kWh**，是全天均值（13,280 kWh）的 **2.68 倍**
- 峰谷比 **22.5 : 1**
- **17:00–22:00 五小时吃掉全天 60% 的电量**
- 峰值时段 **89% 来自家用交流慢充**，公共直流只占 8%

**这意味着什么**：想削峰，盯着公共快充是没用的——**真正的负荷在私人车位上**。这是一个"数据指向非显然结论"的例子：直觉会以为快充桩才是电网压力来源，实际不是。

### ② 快充的真实瓶颈是电池，不是充电桩

![快充功率曲线](figures/02_charge_curve.png)

这是整个项目最有价值的一张图。实际充电功率是**两个限制取较小值**：

```
实际功率 = min( 充电桩额定功率 , 电池当前能接受多少 )
```

左图里阴影区就是实际功率：**平的那段是桩在限制，往下走的那段是电池在限制**，▼ 是两者的交点。

**广为流传的"高功率桩 taper 更早"其实是误读** —— 桩不会 taper，它只是**更早不再成为瓶颈**。同一台车插 60 kW 桩，全程满功率充；插 250 kW 桩，从 16% SOC 起就受电池限制了。

右边是运营层面的后果：

- 直流桩额定平均 **172 kW**，实际只用到 **56 kW**（利用率 **40%**）
- 低电量到达（<30% SOC）利用率 **47%**，高电量到达（>55% SOC）只有 **33%**

**这意味着什么**：如果充电站按"额定功率 × 时间"来预估收入或容量，会高估约 2.5 倍。要提升吞吐量，引导车辆**低电量到达**比换更大功率的桩更有效。

### ③ 低温让直流快充功率掉三分之一

![温度影响](figures/03_temperature.png)

| 温度 | 直流平均功率 | 交流平均功率 |
|---|---|---|
| < 0 °C | **42.4 kW** | 4.5 kW |
| 0–10 °C | 48.8 kW | 5.6 kW |
| 10–20 °C | 59.3 kW | 6.7 kW |
| 20–30 °C | **63.2 kW** | 7.0 kW |

- 直流：0 °C 以下比 20–30 °C **低 33%**
- 交流：夏天稳定在 7 kW（**桩的额定上限**），冬天明显低于上限

**为什么交流也要分开看**：交流桩只有 7 kW，电池在任何温度下都能接受远超这个值。夏天限制来自桩本身，所以看不出温度影响；**冬天是电池变弱了，桩反而吃不饱**。把两者混在一起平均，这个效应会被完全掩盖——这也是我一开始犯的错。

### ④ 没有私人充电桩的车，公共快充使用频次高 8.9 倍

![家充条件的影响](figures/04_home_access.png)

| | 有私人桩（178 台） | 无私人桩（82 台） |
|---|---|---|
| 期内充电总次数 | **69.5 次** | **29.1 次** |
| 其中直流快充 | **1.1 次** | **10.0 次** |

- 没桩的车**总充电次数不到一半**（因为公共充电更贵更麻烦，能拖就拖）
- 但**直流快充频次高 8.9 倍**

**这意味着什么**：公共快充需求主要由**"有没有私人桩"这个结构性条件**驱动，而不是由行驶里程驱动。

⚠️ **一个容易犯的统计错误**：不能拿"两组的直流总次数"直接比，因为两组车辆数不同（178 vs 82）。而且**比值的平均值 ≠ 平均值的比值**——我第一版图表里就是因为先年化再取比，得出了 6 倍而非 8.9 倍，同一个发现出现了两个数字。正确的做法是先算每车均值，再取比。

### ⑤ 连接器有 47% 的时间被"充完没走"的车占着

![连接器占位](figures/05_connector_occupancy.png)

- 全部站点：连接器被占用 **59,401 小时**，其中 **28,040 小时（47%）是充完没走**
- 家用慢充：充 126 分钟 + 占位 **120 分钟**（占位占 49%）
- 单位慢充：充 153 分钟 + 占位 **148 分钟**（49%）
- 公共慢充：充 211 分钟 + 占位 45 分钟（18%）
- 公共直流：充 27 分钟 + 占位 3 分钟（11%）

**这意味着什么**：快充站几乎没有占位问题（司机在等），**占位是慢充站的病**。加"超时占位费"的收益主要在住宅和办公场景，不在快充站。

### ⑥ 电网到电池总损耗 9.1%

| 环节 | 损耗 |
|---|---|
| 交流慢充（车载充电机） | 10% |
| 直流快充 | 6% |

合计 **21,859 kWh** 的损耗。单看不大，但它是**可以定价的**：这部分电费由谁承担，是充电运营的定价问题。

## 3. 怎么复现

**环境要求**：Python 3.10+，依赖 `numpy`、`pandas`、`matplotlib`。

```bash
# 1. 生成数据（约 3 秒）
python -m src.generate

# 2. 看分析报告
python -m src.analyze

# 3. 出图
python -m src.plots

# 或者一次跑完（约 9 秒）
python -m src.main
```

常用参数：

```bash
python -m src.generate --days 30 --vehicles 50   # 小样本快速验证
python -m src.main --skip-generate               # 复用已有数据，只重跑分析和图表
```

**测试**：

```bash
python -m pytest tests/ -q          # 需要 pytest
python scripts/run_tests.py         # 项目自带的 runner，无需 pytest
```

26 个测试覆盖物理不变量、行为不变量和工程不变量（详见第 5 节）。

### 本机环境说明（依赖为什么在 `vendor/` 里）

开发这台机器上有 **7 个不同的 Python**，而 `PATH` 里默认的那个
（`D:\python-3.11.1-amd64`）只有 `numpy` —— 直接跑会报
`ModuleNotFoundError: No module named 'pandas'`。

解决办法是把依赖装进**项目内的 `vendor/` 目录**，再由
[`.vscode/settings.json`](.vscode/settings.json) 通过 `PYTHONPATH` 注入：

```powershell
# 重建 vendor/（约 200 MB，用清华镜像；官方源在国内很慢，不是不通）
python -m pip install --target vendor `
    -i https://pypi.tuna.tsinghua.edu.cn/simple `
    "numpy>=1.24" pandas matplotlib pytest
```

这样做的好处是**不污染任何全局 Python 环境**，换台机器只要重跑这一条命令。
`vendor/` 已 gitignore（体积大，且一条命令就能复现）。

> 注：往全局 Python 装会失败，因为 pip 要往 `%APPDATA%\Python\Python311`
> 写用户级脚本，在没有相应写权限时会被拒绝（`WinError 5`）。`--target` 绕开了这一点。

**用 VSCode**：打开项目后新开一个终端就行，配置会自动生效。若终端是在改配置
之前开的，关掉重开一个。验证：

```powershell
python -c "import pandas; print(pandas.__version__)"
```

**不想用 `vendor/`** 也可以：任何装了 `pandas` + `matplotlib` 的解释器都能跑，
用 VSCode 右下角切换即可 —— 例如
`C:\Users\徐鸿基\Desktop\神经网络\.venv3.11.1\Scripts\python.exe` 就是现成的。

## 4. 模型是怎么校准的

这是整个项目**最花时间、也最值得讲**的部分。数据虽然是合成的，但**物理和电池行为是对着实测数据校准的**。

### 充电曲线

用公开发表的逐 1% SOC 实测充电曲线（EVKX 数据库）校准：

| 对照点 | 实测 | 模型 | 误差 |
|---|---|---|---|
| Tesla Model 3 P @ 20% SOC | 230 kW | 230.4 kW | **+0.2%** |
| Tesla Model 3 P @ 50% SOC | 96 kW | 108 kW | +12.5% |
| Tesla Model 3 P @ 80% SOC | 46 kW | 48 kW | **+4.3%** |
| Tesla Model 3 P 10→80% | 33 min | 30 min | **−8%** |

**误差范围必须说清楚**：接受能力曲线表是**按 Model 3 Performance 拟合**的，对另一台车（VW ID.4 Pro）的误差更大：

| VW ID.4 Pro | 实测 | 模型 | 误差 |
|---|---|---|---|
| 80% SOC 瞬时功率 | 73 kW | 46 kW | −37% |
| 10→80% 时长 | 28 min | 34 min | +22% |

**这不是拟合不够好，而是单张表表达不了两台不同的车**：实测中 ID.4 在 80% SOC 仍能接受峰值功率的 94.8%，而 Model 3 P 只有 57.5%——两块电池的接受曲线**本质不同**（不同电芯、不同 BMS 限值）。生产系统会按车型存曲线；本项目用一张共享表，并把误差**显式断言在测试里**（`test_taper_cross_vehicle_error_is_bounded`），而不是假装没有。

### 低温能耗

用 DOE 引用的一项**五车气候舱受控实验**（AAA 执行）校准：

| 温度 | 实测续航变化 | 模型能耗变化 |
|---|---|---|
| −7 °C（开暖风） | −41% | **+39%** |
| −7 °C（不开暖风） | −12% | — |
| 35 °C（开空调） | −17% | +17% |

### 这轮校准推翻了我最初的三条结论

值得一提，因为它说明了"先验证再往下做"的价值：

| 发现 | 校准前（错） | 校准后 |
|---|---|---|
| 快充实际功率 | 额定的 86% | **40%** |
| 快充平均功率 | 121 kW | **56 kW** |
| 快充平均时长 | 15 分钟 | **27 分钟** |
| 低温影响 | 看不出来 | **−33%** |

**校准前的模型不是"跑不起来"，而是"跑得很好、数据看着也合理、结论全是错的"。** 这类错误不会报错，只能靠拿真实数字去对。

## 5. 测试在测什么

26 个测试分三类。它们存在的理由很具体——**下面每一条都对应一个真实发生过的 bug**：

**物理不变量**
- 充电功率不能超过桩额定功率 → *曾经 60 kW 的桩输出了 100 kW*
- 充电功率不能超过电池接受能力
- 接受能力曲线必须随 SOC 单调不增
- 充电曲线必须复现实测功率点 → *taper 模型错了两次，误差 132% 和 38%*
- 大电池的"瓶颈切换点"必须更晚 → *这是"高功率桩 taper 更早"现象的机制*

**行为不变量**
- 车队平衡 SOC 必须落在合理区间 → *曾经漂到 70%，导致所有充电都挤在 taper 区*
- 家用充电必须在傍晚出现高峰 → *验证高峰是涌现的而非硬编码的*
- 没私人桩的车必须更多使用直流快充
- 交流桩不能给别家车充电（私人桩归属）
- 季节必须跟日历一致 → *曾经季节完全反转：1 月 28°C、7 月 4.6°C*

**工程不变量**
- 相同随机种子必须完全复现
- 不同种子必须产生不同数据
- 预热期的会话不能进入输出
- 日汇总必须覆盖每一天

> **季节反转那个 bug 特别值得说**：温度数据单独看完全正常（平滑、有季节性、范围合理），所有其他测试都通过。**只有把"月份"和"温度"对起来看**才发现是反的。根因是用"运行第几天"驱动季节曲线，而运行起点是 10 月——所以"第 0 天"被当成了 1 月。改成用日历日（day-of-year）后与运行起点无关。

## 6. 局限性（请务必读完再引用任何结论）

### 数据是合成的

没有可自由获取的中国城市充电数据集，所以会话是生成的。生成器编码的是**行为假设**（通勤时间、日行驶里程分布、目标 SOC、插枪频率），因此：

- **"傍晚高峰占 60%" 是这些假设的推论，不是对某城市的观测。**
- 如果真实城市的通勤结构、家充比例或电价机制不同，结论会变。
- 本项目展示的是**方法**：怎么从一份会话日志走到一个站得住脚的运营判断，以及怎么排除假象。

### 参数来源与可信度

每项参数都标注了来源等级（`standard` / `typical` / `demo-only`），完整清单和逐条来源 URL 在 [`docs/charging_behavior_sources.md`](docs/charging_behavior_sources.md)。

**仍未解决的最大缺口**：单次充电时长、单次电量、起止 SOC 的**真实分布**没找到可引用来源（INL EV Project 报告是 PDF，ACN-Data 需要注册 token）。这几项目前来自行为假设。

### 模型简化

- 充电曲线用单张 C-rate 表，**跨车型误差最高 37%**（见第 4 节）
- 未建模：站点总功率上限、排队与等待、电芯温度对接受能力的分段影响
- 交流充电曲线假设恒功率 + 尾部衰减；**衰减拐点无直接出处，是推断**
- 温度只影响充电功率和环境温度，未建模电池热管理预热过程

### 如果要做成真实分析

最直接的路径是接入公开真实数据集：

- **UrbanEV**（深圳，24,798 个桩，6 个月，**CC0 完全开放**）
- **ST-EVCDP**（18,061 个桩，30 天，5 分钟级，全开放）
- **ACN-Data**（Caltech，字段最全，需免费注册 token）

生成器的输出 schema 是按这些数据集的字段设计的，替换数据源不需要改分析层。

## 7. 代码结构

```
charging-insights/
├── src/
│   ├── generate.py    数据生成：电池物理 + 用户行为 + 故障场景（~1000 行）
│   ├── analyze.py     6 项分析，输出可读报告和 JSON（~600 行）
│   ├── plots.py       图表生成，含中文字体处理（~500 行）
│   └── main.py        一键入口
├── tests/
│   └── test_generate.py   26 个测试
├── scripts/
│   └── run_tests.py   自带测试 runner（无 pytest 也能跑）
├── figures/           生成好的图表（已提交，README 直接引用）
├── docs/
│   └── charging_behavior_sources.md   参数来源汇编（408 行，全部带 URL）
├── .vscode/
│   └── settings.json  钉住 PYTHONPATH -> vendor/（已提交，见第 3 节）
├── vendor/            项目内依赖（已 gitignore，一条命令可重建）
└── data/raw/          生成的数据（已 gitignore，可复现所以不提交）
```

### 几个值得说的设计决策

**为什么把物理参数集中在一个文件里**
`generate.py` 顶部所有常量都带来源标注（`[Behav]` 行为假设 / `[Phys]` 物理关系 / `[TODO]` 待考证）。审阅者可以一次看完整个模型的假设，不需要在代码里翻找。

**为什么用查表插值而不是拟合曲线**
接受能力曲线用分段线性插值，因为：BMS 实际就是这么实现的；查表不会像拟合曲线那样过冲；实测点可以直接填进去。

**为什么每一张图上都印着"合成数据"**
图比文字传播得远。一张看起来像真实测量的图如果不说清楚，就是误导。

**中文 Windows 的两个坑**
- 控制台是 GBK 编码，输出 `⚠` 这类字符会直接崩溃 → `analyze.py` 里强制 stdout 用 UTF-8
- matplotlib 默认没有中文字体，所有标签渲染成方块 → `plots.py` 里探测可用字体，并关掉 `axes.unicode_minus`（否则负号也是方块）

## 8. 数据字典

`sessions.csv` 主要字段：

| 字段 | 含义 |
|---|---|
| `session_id` / `vehicle_id` / `station_id` | 标识 |
| `station_type` | `HOME_AC` / `WORK_AC` / `PUBLIC_AC` / `PUBLIC_DC` |
| `start_time` / `end_time` | 会话起止时间 |
| `duration_min` | 充电时长（分钟） |
| `idle_min` | **充完之后的占位时长**（分钟） |
| `energy_kwh` | 充入电池的电量（pack 侧） |
| `energy_grid_kwh` | 从电网取的电量（含损耗，用于计费口径） |
| `avg_power_kw` / `peak_power_kw` | 时间加权平均功率 / 峰值功率 |
| `start_soc` / `end_soc` | 起止电量 |
| `battery_kwh` | 车辆电池容量 |
| `temp_c` | 会话期间环境温度 |
| `power_curve` | 功率曲线采样（逗号分隔，便于抽查） |
